Date: 2026-08-23
Auditor: ox-alpha (read-only mode, no flashing or hardware write)
Scope: determine if any U11→EZE4 difference can prevent M2 (first printk) or M3 (/init as PID 1)
Physical target: SM-X510 Wi-Fi, stock EZE4/U12 firmware

## Real Risk Hypotheses Table (Not Originating from DT Diff)

Known DT differences create zero M2/M3 risk. Real risks stem from the boot contract not captured by DT:

| Hypothesis | Failure Mechanism | Observable Symptom | Probability | Validation |
|---|---|---|---|---|
| H1: AVB/vbmeta rejects unsigned boot image | Bootloader never hands control to kernel | Download/recovery mode or Samsung warning; zero custom kernel activity | High if flashed without managing AVB | Observe device behavior without console; manage vbmeta disable-verification before flashing |
| H2: UART0 physically inaccessible/disabled on EZE4 hardware | Kernel emits printk correctly but no physical channel exists | Total silence ≠ "no boot" | High (most probable scenario today) | Test alternative earlycon, USB serial gadget, ramoops/pstore |
| H3: Initramfs format/size incompatible with EZE4 bootloader | Kernel cannot find valid /init → root mount panic | If console exists: visible panic. No console: reboot loop | Medium | Margin already verified (1.7 MB); test gzip vs lz4; verify metadata |
| H4: U11 kernel crashes pre-printk due to firmware/bootchain mismatch | Hang in timer/PSCI/memory calibration before any console driver | Zero UART bytes + possible reboot loop | Low (PSCI/timer/GIC identical in DT) | Only ruling out with JTAG or pstore post-crash |
| H5: PSCI mismatch between EZE4 EL3 firmware and U11 kernel | SMC rejected → early hang | First printk appears then hang before /init | Low (PSCI node identical) | Any early printk partially rules this out |

## Conclusion Focused on M2/M3

- **Demonstrated risk in DT: none.** The 4 known differences are cosmetic for the M2→M3 path.
- **Major real risk:** not DT content, but handover and observability.
  1. AVB/signing — can prevent reaching kernel execution.
  2. Observability channel — device may boot successfully without detection.
  3. Format/initramfs — can cause panic after first printk.

## Offline Plan to Maximize Probability of First Observable Message

Without touching the tablet yet, prepare:

1. **Earlycon in cmdline**: verify `CONFIG_SERIAL_EARLYCON=y` (✅ already present). Prepare alternate cmdline `earlycon=exynos4210,mmio32,0x13800000 console=ttySAC0` in addition to `console=ram`. Provides earliest possible message if UART0 exists physically.
2. **USB serial gadget in minimal initramfs**: include DWC3 modules + `CONFIG_USB_G_SERIAL=m` or configfs gadget. More realistic alternative if UART0 is not exposed.
3. **Ramoops/pstore with fixed address**: reserve region in U11 DT reserved-memory (offline), point `ramoops.mem_address=... mem_size=...`. Extract log via recovery/ADB after a crash even if no live console ever existed.
4. **Two parallel initramfs images**: one minimal with busybox+sh (maximum probability of successful /init), another with USB gadget for observability. Alternate across successive boots.
5. **Verify complete cmdline**: `console=ram printk.devkmsg=on` present ✅. Add earlycon conditionally.
6. **Expected capture points**:
   - Zero UART bytes + zero screen display → pre-kernel issue (AVB/bootloader).
   - Partial bytes + hang → timer/PSCI/memory issue.
   - Full printk + no /init → initramfs issue.
   - Everything works but invisible → purely observability issue.

Each physical contact thus becomes a step-by-step binary experiment, rather than a blind attempt.

## Unknowns That Only Hardware Can Resolve

- Which overlay (r00/r01/r04) does the bootloader select on the physical unit?
- Does AVB accept or reject the unsigned candidate? (observable behavior without UART)
- Does the kernel actually reach printk emission? (requires capture channel)
- Does the minimal initramfs successfully reach /init? (requires M2 first)
