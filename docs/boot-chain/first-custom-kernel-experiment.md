# First custom EZE4 kernel experiment — design only

Goal: prove that the project-built EZE4 kernel executes. It is not a Linux userspace, sec_debug, display or peripheral bring-up test.

Status: **NOT READY FOR EXECUTION** until unlock and recovery gates pass. No image is generated by this document.

## Preferred experimental shape

The mechanically smallest candidate is **boot only**, leaving stock `vbmeta`, `init_boot`, `vendor_boot` and `dtbo` untouched. This is conditional on future evidence that the unlocked Samsung bootloader accepts the resulting root/embedded boot verification error. If it does not, stop; do not automatically escalate to modified vbmeta.

## Intrinsic positive marker

Build the already validated EZE4 configuration with fixed, experiment-specific build identity while preserving `UTS_RELEASE` and vermagic:

```text
KBUILD_BUILD_USER=gts9fe-marker
KBUILD_BUILD_HOST=eze4-exp01
KBUILD_BUILD_VERSION=<recorded integer>
KBUILD_BUILD_TIMESTAMP=<fixed recorded value>
```

Before any packaging, prove offline that:

- `make kernelrelease` remains `5.15.189-android13-3-33478785`;
- module vermagic/CRC parity remains intact;
- the expected marker appears in the built kernel banner and `/proc/version` representation;
- the Image hash differs from stock and is recorded;
- a stock-image unpack/repack round trip preserves boot v4 fields, offsets, partition size and untouched components.

Build user/host changes `UTS_VERSION`/banner without changing `UTS_RELEASE`; this must still be mechanically verified. A source-code marker or forced reboot is unnecessary unless this approach fails offline.

## Expected success

Stock Android boots and ADB returns the exact pre-recorded marker from `/proc/version`/`uname -a`. This is a positive, kernel-owned signal. Normal Android boot alone is insufficient unless the marker is read.

## Failure signatures

| Observation | Meaning |
|---|---|
| Samsung verification warning/rejection before Android | Boot policy rejected the modified boot; kernel execution not shown |
| Bootloop/hang with no intrinsic marker recovered | Ambiguous AVB versus early kernel failure |
| USB/current/backlight transition only | PLAUSIBLE activity, not proof of kernel execution |
| Marker readable and expected Image identity recorded | CONFIRMED custom-kernel execution |

sec_debug/DSS is not assumed to catch the first failure: AVB rejection precedes it and modular sec_debug may not yet be loaded. Do not add arbitrary ramoops memory.

## Rollback design

If boot was the only modified partition, restore the exact stock EZE4 boot through the previously validated recovery path, then verify Android boot, marker absence, Download Mode and security properties. If any other partition was changed, restore every changed partition; never use a boot-only rollback after a vbmeta/init_boot/vendor_boot change.

## Escalation boundary

Only after a boot-only policy result is unambiguous may a separately reviewed experiment consider vbmeta. Controlled Linux `/init` is a later experiment and likely introduces `init_boot`; it must not contaminate this first kernel-execution test.
